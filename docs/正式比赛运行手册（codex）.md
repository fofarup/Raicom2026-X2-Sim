# 睿抗 2026 X2 正式比赛运行手册（Codex）

> 用途：真机调试和单任务验收全部通过后，指导现场队员完成正式计分运行。
>
> 操作方式：由现场操作员通过 SSH 操作 X2 的 PC2；Codex 不连接、不操作、不控制真机。
>
> 重要：本文不是当前代码的“立即可运行证明”。未通过《真机调试指南（codex）》全部门禁时，不得直接照本文启动机器人。

---

## 1. 适用前提

正式比赛前，必须已经完成以下工作：

- [ ] 目标 X2 的固件和 AimDK 版本已经冻结。
- [ ] 项目 commit SHA 已完成真机验收，比赛当天不再临时改代码。
- [ ] 真机启动路径不再出现 MuJoCo Reset 等仿真操作。
- [ ] 真机模式明确使用 `--no-sim`，且启动日志会醒目显示“真机模式”。
- [ ] 地图、重定位、导航坐标和场地区域已经标定。
- [ ] 激光避障、点云断流停车和定位失效停车已经通过。
- [ ] 相机、ASR、自研 TTS、表情、手势均已用真实设备验证。
- [ ] 物品检测、夹爪反馈、物品离桌和保持已经形成真机闭环。
- [ ] 三个任务分别至少连续通过三次。
- [ ] 完整状态机已经按正式规则完成一次不间断运行。
- [ ] 失败时不会虚假播报成功，并能可靠停止。
- [ ] 裁判已确认赛前允许启动哪些基础节点、何时开始计时以及是否允许重定位。

只要有一项未满足，正式比赛策略应当是先解决阻断项，而不是现场碰运气运行整套程序。

## 3. 现场人员分工

建议至少三人明确分工：

| 角色 | 主要职责 | 正式运行期间 |
|---|---|---|
| 操作员 | SSH、环境检查、执行唯一启动命令 | 不进行人工遥控或临时改参 |
| 交互队员 | 按规则完成语音、展示卡片和需求交互 | 只做规则允许的交互 |
| 安全员 | 观察机器人、围挡、人员和急停条件 | 发现危险立即要求终止 |

所有人赛前统一口令：

- “准备”：只允许检查，不触发机器人动作。
- “启动”：仅在裁判明确下令后，由操作员执行唯一启动命令。
- “停止”：立即按已验证的停止流程处理，不讨论、不等待。
- “结束”：保存日志，不擅自进行第二次运行。

## 4. 赛前一天

### 4.1 冻结代码

在笔记本执行：

```bash
cd ~/x2_ws/x2_biao
git fetch origin main
git status -sb
git rev-parse HEAD
git log -1 --oneline
```

要求：

- 工作区无不明改动；
- commit 与真机验收版本完全相同；
- 不在比赛当天执行 `git pull` 获取未经验证的新代码；
- 密钥、现场地图和模型已经安全备份，但没有误提交到公开仓库。

建议准备两个只读部署包：

1. 主 U 盘：冻结版本代码、模型、地图转换文件、依赖离线包；
2. 备份 U 盘：内容与主 U 盘一致，并记录 SHA256。

### 4.2 冻结启动流程

正式启动不能依赖操作员临场回忆。将经过真机验证的命令填写到冻结表，至少明确：

1. AimDK 环境脚本；
2. map/TF 节点是否赛前启动；
3. SLAM 重定位由哪个已验证节点完成；
4. 竞争节点的真机参数；
5. 日志保存方式；
6. 正常和紧急停止方式。

如果裁判要求“三个任务只能接受一次启动命令”，应把必要启动动作封装为一个已经测试过的入口脚本。不要在比赛当天临时写脚本。

### 4.3 离线物料

- [ ] 项目冻结副本。
- [ ] Python/系统依赖离线安装包。
- [ ] ASR 和 TTS 模型。
- [ ] 现场地图及转换后的 YAML。
- [ ] AimDK 官方接口快照。
- [ ] 本手册打印版和冻结表。
- [ ] 网线、USB 网卡、U 盘及备用设备。
- [ ] 笔记本电源和充电器。

## 5. 到达现场后的时间线

以下时间为建议值，以组委会实际安排为准。

### T-90 分钟：场地和规则确认

先向裁判或技术支持确认：

- 机器人型号、末端执行器和固件是否与验收机一致；
- 比赛前是否允许启动 ROS 基础节点；
- 比赛前是否允许完成重定位；
- 计时从裁判口令、程序启动还是机器人动作开始；
- 正式运行失败后是否允许再次启动；
- 急停、机器人恢复和人员进入场地的规则；
- 地图 `map_id`、起点以及区域边界是否变化。

规则不明确时先问裁判，不用自己的理解替代现场裁决。

### T-75 分钟：建立网络和 SSH

笔记本连接机器人背部 SDK 二次开发网口。先查看网卡名：

```bash
ip -br link
ip -br addr
```

由操作员在正确网卡上配置冻结的静态地址，然后：

```bash
ping -c 3 10.0.1.41
ssh agi@10.0.1.41
```

禁止把 PC1 `10.0.1.40` 作为开发环境，也不在没有技术支持指导时管理 PC1 服务。

### T-65 分钟：确认机器人版本

以下均为只读检查：

```bash
uname -a
cat /etc/os-release
python3 --version
echo "ROS_DOMAIN_ID=${ROS_DOMAIN_ID:-未设置}"
echo "RMW_IMPLEMENTATION=${RMW_IMPLEMENTATION:-默认}"
```

按冻结表 source 已验证的 AimDK 环境，然后检查：

```bash
ros2 pkg prefix aimdk_msgs
ros2 node list
ros2 topic list -t
ros2 service list -t
```

只要 AimDK、固件、消息字段或 ROS 域与冻结值不同，就停止进入下一阶段，联系技术支持并重新评估兼容性。

### T-55 分钟：核对部署版本

在 PC2 执行：

```bash
cd ~/raicom2026_competition
git rev-parse HEAD 2>/dev/null || true
python3 -m compileall -q competition_node.py core ik_sdk
```

如果 PC2 部署副本不是 Git 仓库，应在部署包中保存 `VERSION.txt` 并核对完整 SHA。

禁止现场使用编辑器临时修改以下内容：

- 启动模式；
- 场地坐标；
- 速度；
- 关节角；
- 夹爪力度；
- 输入源优先级和超时；
- 识别阈值。

确实发生场地变化时，应退出正式运行准备，按真机调试流程重新验收，不把未经验证的参数用于计分运行。

### T-45 分钟：只读接口快速检查

```bash
ros2 topic type /aima/mc/locomotion/velocity
ros2 topic type /aima/hal/sensor/lidar_chest_front/lidar_pointcloud
ros2 topic type /aima/hal/sensor/rgbd_head_front/rgb_image
ros2 topic type /slam/lidar_odom
ros2 service type /aimdk_5Fmsgs/srv/SetMcInputSource
ros2 service type /aimdk_5Fmsgs/srv/PlayEmoji
```

再检查关键数据频率：

```bash
timeout 5 ros2 topic hz /aima/hal/sensor/lidar_chest_front/lidar_pointcloud
timeout 5 ros2 topic hz /aima/hal/sensor/rgbd_head_front/rgb_image
timeout 5 ros2 topic hz /slam/lidar_odom
```

失败条件：话题不存在、类型改变、持续无数据、时间戳停滞或 QoS 不兼容。失败时不启动比赛程序。

### T-35 分钟：地图和重定位

本步骤是否可在计时前执行，必须听从裁判。

标准逻辑：

1. 使用正确 `map_id` 触发 `start_relocalization:<map_id>`；
2. 约一秒后发布冻结的像素初始位姿；
3. 收到 `/slam/lidar_odom` 后才算成功；
4. 核对 `map → base_link` 与实际起点、朝向一致。

操作员只运行赛前已经验证的重定位节点，不在现场手写 `ros2 topic pub` 命令。

只读检查：

```bash
timeout 10 ros2 topic hz /slam/lidar_odom
timeout 5 ros2 run tf2_ros tf2_echo map base_link
```

通过标准：定位连续、数值有限、静止漂移正常、坐标和朝向与起点一致。定位跳变时不得靠修改目标坐标“抵消”。

### T-25 分钟：无运动交互检查

在裁判允许的情况下，只做不会让机器人身体运动的检查：

- 相机有真实画面；
- 麦克风有输入；
- 自研 TTS 生成的音频能通过 PC3 扬声器播放；
- `PlayEmoji` 服务及状态话题正常；
- 本地时间和时区正确；
- ASR、TTS 模型均可离线加载。

不要在此阶段试走、试转、挥臂或抓取。运动功能应在此前场地适应和正式验收时完成。

### T-15 分钟：建立终端布局和日志

推荐至少保留三个 SSH 终端：

| 终端 | 用途 | 是否发送运动命令 |
|---|---|---:|
| A | 正式程序和完整日志 | 裁判下令后由程序发送 |
| B | 只读观察定位、节点和系统状态 | 否 |
| C | 安全员使用的已验证停止流程 | 仅在停止时 |

创建日志目录：

```bash
mkdir -p ~/raicom_competition_logs
run_id=$(date +%Y%m%d_%H%M%S)
run_dir=~/raicom_competition_logs/${run_id}
mkdir -p "$run_dir"
printf '%s\n' '<冻结的完整 commit SHA>' > "$run_dir/commit.txt"
ros2 node list > "$run_dir/nodes_before.txt"
ros2 topic list -t > "$run_dir/topics_before.txt"
ros2 service list -t > "$run_dir/services_before.txt"
```

如果使用 `tmux`，必须是赛前已经熟练验证的布局。比赛现场不临时学习快捷键。

### T-10 分钟：启动被允许的被动基础节点

只有裁判允许时，才在计时前启动不产生机器人运动的基础节点，例如：

- 已验证的地图发布节点；
- TF/定位转发节点；
- 只读监控和日志节点。

项目 `map_tf_distribution` 需要已经转换并验证的 ROS map YAML。例如冻结流程可能是：

```bash
source <冻结的 AimDK 环境脚本>
source ~/raicom_map_ws/install/setup.bash
ros2 launch map_tf_distribution map_tf_bringup.launch.py \
  map_yaml:=<冻结的绝对 YAML 路径> \
  rviz:=false
```

尖括号必须替换为冻结表中的真实值。该节点只会从已有 `map → base_link` TF 转发位姿，不会代替官方 SLAM 重定位。

启动后确认没有任何非零速度或手臂/夹爪命令发布者意外运行。

### T-5 分钟：最终 Go/No-Go

队长逐条询问，操作员回答“通过”或“停止”：

- [ ] 机器人、固件、AimDK 和 commit 与冻结表一致。
- [ ] ROS 域、消息类型和服务一致。
- [ ] 定位连续、起点及朝向正确。
- [ ] 激光、相机和交互设备正常。
- [ ] 正式程序没有提前启动。
- [ ] 没有未知控制节点或冲突输入源。
- [ ] 日志已经开始准备，但不会影响实时性。
- [ ] 操作员终端位于正确目录和正确环境。
- [ ] 唯一启动命令已经核对，但尚未执行。
- [ ] 交互队员清楚全部口令、站位和规则。
- [ ] 安全员清楚停止条件和停止方法。
- [ ] 裁判允许进入正式运行。

任一项为“No-Go”，不要启动。

## 6. 裁判下令后的正式启动

### 6.1 唯一启动原则

裁判明确下令前：

- 不按回车；
- 不切换会导致动作的模式；
- 不发送速度、手臂或夹爪命令；
- 不让队员提前说任务口令。

裁判下令后，由一名操作员执行冻结表中的唯一启动命令。其他人不得同时操作终端。

在当前 argparse 定义中，真机标志是：

```bash
--no-sim
```

不是“不加 `--sim`”。无参数启动当前仍会进入仿真模式。

当 B-01 至 B-11 全部关闭、该命令已完成真机验收时，正式入口预计类似：

```bash
cd ~/raicom2026_competition
python3 -u competition_node.py --no-sim 2>&1 | tee "$run_dir/competition.log"
```

最终以冻结表中的已验证命令为准。不要复制一个尚未通过真机验收的示例命令参加比赛。

### 6.2 启动后前十秒

操作员只观察，不输入额外命令：

1. 日志明确显示真机模式；
2. 输入源注册成功，响应码正确；
3. 没有 MuJoCo、Reset、键盘模拟或读取测试图片的日志；
4. 定位数据新鲜；
5. 机器人状态正常；
6. 状态机进入预期任务，而不是等待调试输入。

发现模式错误或仿真提示，立即按已验证流程停止，不能继续运行。

## 7. 三个任务运行期间

### 7.1 任务 1：进入交互区

交互队员按规则说出启动口令。操作员只观察：

- ASR 原始文本及确认结果；
- 定位是否持续更新；
- 导航目标是否为交互区 I；
- 障碍检测和安全状态是否正常；
- 机器人是否完整进入区域并停稳；
- 最终是否正面朝向交互区 II。

不得通过键盘、手柄或人工速度命令修正路线。定位失效、越界、碰撞风险或摔倒趋势出现时，安全优先，终止运行。

### 7.2 任务 2：交互

交互队员按照裁判顺序完成：

1. 时间提问；
2. 展示数字/颜色卡片；
3. 说出表情要求；
4. 说出动作要求。

队员注意：

- 站在预先验收的麦克风和相机有效区域；
- 卡片距离、角度和停留时间采用训练时固定动作；
- 一次只说一个完整指令；
- 机器人要求确认时，只回答明确的“对”或“不对”；
- 不用身体触碰机器人，也不替机器人调整姿态。

操作员观察：识别结果、表情响应、真实关节反馈和机器人扬声器播报。程序日志显示成功但物理动作未完成时，应按实际结果处理，不能人工补动作。

### 7.3 任务 3：需求、作业区和抓取

交互队员说出规则规定的养老服务需求。操作员只观察：

- 需求分类和应答是否一致；
- 机器人是否自主进入作业区并停稳；
- 感知结果是否来自真机相机/深度数据；
- 目标类别和三维坐标是否合理；
- 手臂轨迹是否远离身体、桌面和其他物体；
- 夹爪状态是否无故障；
- 正确物品是否完全离开桌面；
- 播报内容是否与实际夹持物一致；
- 播报结束前物品是否保持稳定。

物品未抓住时，不得因为程序进入下一状态就宣称成功。手臂或夹爪异常时立即停止，不现场重复发送抓取命令。

## 8. 运行期间禁止事项

- 禁止人工发布速度命令或遥控修正路线。
- 禁止中途修改代码、参数、坐标或地图。
- 禁止通过键盘替代规则要求的语音交互。
- 禁止重新点击仿真 Reset 或运行任何 MuJoCo 操作。
- 禁止在程序失败后伪造成功日志或播报。
- 禁止在没有裁判许可时进行第二次启动。
- 禁止把云端服务用于规则不允许的实时控制或感知。
- 禁止调用机器人官方现成语音大模型完成受限任务。
- 禁止因“只差一点”而忽略定位、碰撞、摔倒或关节异常。
- 禁止在 PC1 上临时停止 MC 或其他系统服务，除非现场技术支持明确负责并确认后果。

## 9. 异常与停止流程

### 9.1 软件失败但机器人稳定

例如识别失败、服务超时、路径规划失败：

1. 不人工补发动作；
2. 确认程序已持续发布零速度并停止上肢动作；
3. 保存日志和最后状态；
4. 等待裁判指令；
5. 未经裁判许可，不重新启动。

### 9.2 定位或通信故障

出现定位断流、时间戳停滞、SSH 断开、ROS 节点消失：

1. 立即执行赛前验证过的停止流程；
2. 安全员持续观察机器人；
3. 必要时按照 X2 用户手册和现场要求急停；
4. 不依靠断开 SSH 作为唯一停止手段；
5. 不在状态不明时重新连接后直接恢复运动。

### 9.3 物理危险

机器人倾倒趋势、碰撞围挡、靠近人员、手臂撞击或夹爪异常时：

1. 安全员立即喊“停止”；
2. 执行已验证的急停措施；
3. 所有人不要贸然扶机器人；
4. 由现场技术人员按规定恢复；
5. 保存日志并向裁判报告。

安全停止优先于成绩。

## 10. 正常完成后的处理

程序完成三个任务后，应主动停止运动并进入完成状态。操作员确认：

- 机器人速度为零；
- 手臂和夹爪处于验收过的保持/结束状态；
- 状态机只完成一次；
- 没有自动开始第二轮；
- 裁判已确认本轮结束。

随后保存：

```bash
ros2 node list > "$run_dir/nodes_after.txt"
ros2 topic list -t > "$run_dir/topics_after.txt"
cp "$run_dir/competition.log" "$run_dir/competition.log.saved"
sync
```

不要在裁判尚未确认前移动机器人、重新运行节点或清理日志。

记录最终结果：

```text

地图 ID：
任务 1 结果：
```

- [ ] 正式程序尚未启动。
