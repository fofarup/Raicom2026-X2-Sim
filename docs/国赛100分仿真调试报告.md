# 2026 睿抗智慧养老组国赛基础 100 分仿真调试报告

## 1. 结论

本轮在无真机条件下，以 MuJoCo 为主，对国赛修订稿中的基础 100 分项目进行了诊断。调试基线为提交 `bf772f5`，范围不包含自主建图附加 50 分。

本报告是**调试与取证报告，不是修复报告**。本轮未修改任何已有代码、配置或脚本，也未读取或改动 `control/raicom2026/config/` 下的本地文件。

结论如下：

- 当前工程不能证明达到 100 分。
- 按“必须有本轮 MuJoCo 物理状态或可重复测试证据”的保守口径，严格确证 **29/100**。

## 6. 问题清单与根因

### P0-1：当前配置没有启用竞赛叠加模型

**现象**

- `config/project.env` 当前设置 `ROBOT_NAME="lx2501_3_t2d5"`。
- `README.md` 的配置说明写的是 `lx2501_3_t2d5_raicom`，二者不一致。
- `scripts/in_container/start_sim.sh` 只有在名称等于 `lx2501_3_t2d5_raicom` 时，才生成竞赛模型、构建激光插件并启动手臂状态中继。
- 实际进程加载的是基础模型 `.../robot/lx2501_3_t2d5/simulator/default.yaml`。
- ROS 话题中没有 `/aima/sim/lidar/points`。

**影响**

任务 3 能导航到工作区，也能产生目标语义坐标，但无法获得目标物物理位姿反馈，物理抓取链路在入口处终止。基础模型也不能提供本项目期望的完整竞赛道具/夹爪/传感器闭环。

**根因定位**

启动配置、README 声明与竞赛叠加模型的条件分支不一致。

### P0-2：TTS 模型加载成功但没有可用音频输出

**现象**

Piper 模型 `zh_CN-huayan-medium.onnx` 能加载，但每次播报均等待约 8–10 秒后报告：

```text
TTS 无声输出（无模型或无音频设备），仅记录
```

容器内有 `aplay`，但本轮没有可工作的音频设备链路。

**影响**

时间回答、动作名称、需求应答和抓取结果播报均不能按现场可听输出计分；同时多次超时显著拉长流程。

### P0-3：目标语义识别与物理位姿反馈没有闭环

**现象**

抓取阶段先记录水杯的 base 坐标，随后立即报“没有水杯的物理位姿反馈”。

**影响**

任务 3 的 17 分抓取项和 10 分结果播报项无法完成。

**根因定位**

本轮仿真没有加载竞赛物体/传感器反馈链路；抓取逻辑要求的物理目标状态为空，因此安全失败。这与 P0-1 的实际启动模型直接相关。

### P1-1：真实相机同步拍照存在回调饥饿

**复现**

创建 `VisionController(sim=False)`，从另一个节点持续发布合法 `rgb8` 图像，然后在订阅节点上同步调用 `_capture(timeout=0.8)`：调用超时；随后手动 `rclpy.spin_once`，帧立即可见。

**根因定位**

`core/vision.py` 的 `_capture()` 在等待循环中只执行 `time.sleep(0.05)`，没有 spin；主状态机又同步调用该函数。在没有后台 executor 的情况下，订阅回调无法运行。

**影响**

真机模式可能在相机正常发布时仍报 3 秒内没有图像。当前以仿真为主，因此本轮不影响 29 分结论，但会阻断后续真机验收。

### P1-2：ROS 图像转换不支持常见编码与行填充

**复现结果**

- `rgb8`、`height=2`、`width=2`、`step=8` 的带行填充图像：`ValueError: cannot reshape array of size 16 into shape (2,2,3)`。
- `bgr8`：`ValueError: 不支持的图像编码: bgr8`。

**影响**

相机驱动只要输出 BGR 或 `step != width * channels`，拍照识别就会失败。

### P1-3：数字算法对完整相机场景不稳健

**结果**

- 直接读取裁剪好的 63 张素材：63/63 数字正确。
- 将每张卡片缩放后放入 `640x480` 深灰背景，模拟完整相机画面：只有 6/63 数字正确；多数被识别为 0，背景还可能被判为靛蓝色。

**根因定位**

前景提取把整幅画面中的非白色像素视为数字前景，深色背景主导了包围框和颜色统计。现有测试只覆盖白底裁剪图，未暴露该问题。

### P1-4：确认与否认存在包含关系冲突

**复现结果**

```text
_keyword_correct("不对", context="确认") -> "对"
_keyword_correct("不是", context="确认") -> "是的"
```

同时，`is_confirmed("不对")` 会因为包含字符“对”而返回真；调用流程如果先判断确认，再判断否认，就会把拒绝当成确认。“错了”能正确判断为否认。

**影响**

用户拒绝错误的表情、动作或需求识别时，系统可能错误接受，造成任务 2 或任务 3 选择错误。

### P1-5：导航公共入口引用未定义常量

**复现**

当当前位置 `y < -0.50`，调用 `Navigator.goto(*INTERACT_I)`：

```text
NameError: name 'INTERACT_APPROACH' is not defined
```

`core/navigator.py` 使用了 `INTERACT_APPROACH`，但模块中没有定义。当前任务 1 主流程使用专用 `task1_enter_zone()`，因此本轮端到端没有触发；其他调用路径仍然会失败。

### P1-6：已注册的运动安全检查没有被运动循环使用

`Navigator` 将 `mapper.safe_to_advance` 注册到 `MotionController._safety_check`，但检索结果只发现赋值和 setter，没有在直线移动或泊入循环中调用。

**影响**

代码表面上连接了安全检查，实际运动输出不受其约束。仿真场景变化或真机障碍物出现时，不能依赖该接口制动。

## 7. 软件逻辑通过但不能直接计分的能力

以下结果说明已有实现基础，但不等于现场得分：

## 8. 后续修复阶段建议顺序

本轮未执行以下修复，仅给出建议优先级：

1. 统一竞赛机器人配置与启动模型，先让夹爪、目标物和激光/物理反馈话题真实出现。
